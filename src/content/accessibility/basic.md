## 公式ドキュメント・アクセシビリティの基準

アクセシビリティ（A11y）の実装において、独自の判断でマークアップを行うことはバグやアクセシビリティ低下を招きます。実装や設計で迷った際は、必ず以下の世界標準の公式仕様および達成基準に立ち返ってください。

### ⚠️【重要】開発メンバーへの必須要件

本ガイドラインは実務におけるエッセンスをまとめたものであり、WCAGの膨大な達成基準のすべてをこの1ページに網羅することは不可能です。
そのため、**アクセシビリティ目標（レベルA / AA / AAA）が明確に定義された案件にアサインされた際、または実装に少しでも迷った際**は、本ガイドラインの記述にとどまらず、以下に挙げる**2つの公式ドキュメント（WCAG 2.2 および WAI-ARIA APG）の最新仕様を正典として必ず確認し、厳格に準拠**してください。

#### アクセシビリティレベルの公式ページ（WCAG 2.2）
Webコンテンツが満たすべきアクセシビリティの国際基準「Web Content Accessibility Guidelines (WCAG) 2.2」の日本語訳です。アサインされた案件の指定レベル（A / AA / AAA）に応じた達成基準の具体的なロジックと根拠は、すべてこのページに集約されています。
* [WCAG 2.2 公式解説（ウェブアクセシビリティ基盤委員会：WAIC）](https://waic.jp/translations/WCAG22/)

#### 機能別・パターン別の実装公式ガイド（WAI-ARIA APG）
アコーディオン、タブ、モーダルなど、Webアプリケーションで多用される動的UI（デザインパターン）に対して、どのようなHTML構造、WAI-ARIA属性、キーボード操作を提供するべきかが具体的に網羅されている公式カタログです。レベルに適合したセリアライズな動的UIを構築するための「答え」がここに書かれています。
* [W3C WAI-ARIA Authoring Practices Guide (APG)](https://www.w3.org/WAI/ARIA/apg/patterns/)

## セマンティクスとWAI-ARIAの大原則（HTMLとの連携）

WAI-ARIA（`role` 属性や `aria-*` 属性）は、標準のHTMLタグだけでは表現できない「動的な状態」をスクリーンリーダーなどの支援技術に伝えるための強力な仕組みですが、誤った使い方はアクセシビリティを著しく破壊します。

### 第一ルール：「ARIAを使わないことが最善のARIA」
「NO ARIA IS BETTER THAN BAD ARIA」の原則に基づき、HTML標準タグ（ネイティブ要素）で表現できるものは、100%ネイティブ要素で記述してください。デザインを理由に `<div>` や `<span>` に無理やり `role="button"` を付与する行為は原則禁止とします。

### role属性のネイティブ要素への重複禁止

標準のHTMLタグに対して、そのタグが本来持っている意味と同じ `role` を重ねて記述してはいけません。コードが冗長になり、ブラウザの解釈を妨げます。

### 動的UIにおける状態（aria-*）のリアルタイム更新

アコーディオンやモーダルなど、状態が変化するUIを実装する場合は、JavaScriptの操作（「DOM操作とイベントハンドリング」）と完全に連動させて、状態を表す属性値をリアルタイムに変更してください。

```html
<button type="button" aria-controls="faq-answer-01" aria-expanded="true" class="js-accordion-trigger">
  Q. 支払い方法は何がありますか？
</button>
<div id="faq-answer-01" aria-hidden="false" class="c-faq__answer">
  A. クレジットカード決済に対応しています。
</div>
```

## キーボード操作の担保（フォーカス制御）

マウスやトラックパッドを使用できない、または使用しないユーザー（全盲のユーザー、手の怪我、効率的なキーボード操作を好むパワーユーザーなど）のために、すべての操作をキーボードだけで完結させる必要があります。

### すべてのインタラクティブ要素のキーボード操作対応

ボタン、リンク、フォーム入力欄など、クリック可能なすべての要素は `Tab` キーでフォーカスが当たり、`Enter` または `Space` キーで実行できるように、適切な要素（`<a>`, `<button>` 等）で実装してください。

### フォーカスインジケータ（:focus-visible）の視認性確保

「デザイン的に目立って邪魔だから」という理由だけで、CSSで `outline: none;` や `outline: 0;` を指定してフォーカス時の輪郭線を消し去る実装は完全に禁止とします。
現在地を見失わせる原因になります。見た目の調整はモダンCSSの `:focus-visible` 疑似クラスを使用して行ってください。

### モーダル展開時の「フォーカストラップ（Focus Trap）」の実装

モーダルウィンドウ（ポップアップ）を開いた際、`Tab` キーを押し続けたときにフォーカスがモーダルの裏側（非表示になっているメイン画面のリンク）へ逃げてしまってはいけません。
モーダルが開いている間は、フォーカスがモーダル内部の要素だけでループ（循環）する「フォーカストラップ」のロジックをJavaScript側で必ず実装してください。

## スクリーンリーダー（音声読み上げ）への配慮

目の不自由なユーザーが使用するスクリーンリーダー（音声読み上げブラウザ）が、ページの意図や構造を正しく音声変換できるように、マークアップを最適化します。

### 画像要素における alt 属性の厳格な書き分け

すべての `<img>` タグには `alt` 属性の記述が必須ですが、その中身は画像の役割（「画像要素の適切な使い方」）に応じて厳密に書き分けてください。

- 情報を持つ画像（バナー、図、写真）： その画像が伝えている具体的なテキストや内容を記述する。
- 装飾目的の画像（背景、カスタムアイコン、飾り）： 必ず `alt=""`（空文字） を明記して、スクリーンリーダーが無視してスキップできるようにする（alt 属性自体を書かないのはNGです）。

### 視覚情報のみの要素に対する非表示テキスト（.visually-hidden）の提供

デザイン上、アイコンのみで表現されているボタン（例: ✕マークだけの閉じるボタン、虫眼鏡だけの検索ボタン）は、音声読み上げでは「ボタン」としか発音されず、何のボタンか理解できません。画面上は非表示にしつつ、スクリーンリーダーにだけ読ませる専用のCSSクラス（`.visually-hidden`）を用いて隠しテキストを配置してください。

```html
<button type="button" class="c-closeButton js-modal-close">
  <span class="visually-hidden">このモーダルを閉じる</span>
  <span class="c-icon-close" aria-hidden="true">✕</span>
</button>
```

```scss
.visually-hidden {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  border: 0;
}
```

## 自動検証ツールの実行（必須化）

コーディングが完了したら、ブラウザでの見た目チェックだけでなく、必ず以下の手法を用いてアクセシビリティのクオリティをセルフチェック（検証）してください。

- [Google Lighthouse](https://chromewebstore.google.com/detail/lighthouse/blipmdconlkpinefehnmjammfjpmpbjk?hl=ja)
  - 「Accessibility」の項目を計測し、95点以上が担保されていることを確認します。
- [axe DevTools](https://chromewebstore.google.com/detail/axe-devtools-web-accessib/lhdoppojpmngadmnindnejefpokejbdd?hl=ja)
  - 現場のプロが最も多用するアクセシビリティ検証プラグインです。ページ内のコードをスキャンし、WCAGのどの達成基準に違反しているかを具体的に一瞬で洗い出してくれるため、開発中の常時チェックへの導入を強く義務付けます。
